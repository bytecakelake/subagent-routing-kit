# 하이브리드 라우팅 설계: 규칙 코드 + 전용 결정 모델 + 고성능 부모

## 상태

2026-10-30 조사·설계 단계. 운영 설정, 부모 모델, 17개 model_map 경로는 변경하지 않았다. Jev API는 호출하지 않았다(Docker에서 OpenRouter 키를 읽을 수 없고, 유료 호출 승인도 없었다). 아래 정확도·절감 효과는 검증된 수치가 아니라 **검증해야 할 가설**이다.

## 결론

전용 결정 모델은 **라우팅 추천과 사전 필터링**에 적합하다. 다만 안전·자격 조건은 신경망에 맡기지 않고 코드로 고정하고, 애매하거나 위험한 건은 고성능 부모가 결정한다.

```text
요청/작업
  ① 규칙 코드: 자격·금지 조건 확정 (모달리티, 입력 길이, 쓰기 범위, 승인, 활성 option, 옵션 호환, 무료→유료 금지)
  ② 결정 모델(Jev 등): 작업 유형·난도·위험·검토 필요성을 확률로 분류 → 추천 티어/변형
  ③ 게이트: 확신 높고 저위험 → 추천 채택 / 낮은 확신·고위험·충돌 → 부모 판단
  ④ 고성능 부모: 최종 배정·승격·중단
  ⑤ 실행 후 결과와 비용을 기록 → 임계값 재보정
```

## 조사한 방식

| 방식 | 하는 일 | 이번 구성에서의 판단 |
|---|---|---|
| Jev Decisions API | 상태+질문을 받아 Choice/Noul/Score 형식의 타입 답과 확률 반환. 텍스트·추론 설명 없음 | **분류·위험 판정·검증 게이트에 적합**. 라우팅 추천기로 1순위 후보[17][20][21] |
| Jev Router (`typesafe/jev-router`) | 요청마다 모델과 추론 강도를 선택해 그 모델이 응답 생성. cost_tier·모델 포함/제외 선호 지원 | **자동 선택기이지 명시적 변형 체계의 대체재가 아님**. 실험용 후보[16] |
| RouteLLM | 강/약 두 모델 사이 라우팅. BERT·행렬분해 등. 임계값 보정 | 17개 변형·추론 옵션 선택에는 구조가 맞지 않음. 비용 임계값 보정 아이디어만 참고[18] |
| vLLM Semantic Router | 신호 추출→정책→후보 선택→모델 풀. 자격 조건을 먼저 두고 최적화를 나중에 적용 | 구조 원칙은 이번 설계와 일치. 자체 운영형 인프라라 현 단계에는 과함[19][23] |

## 전용 결정 모델이 맞는 일 / 맞지 않는 일

| 맞는 일 | 맞지 않는 일 |
|---|---|
| 작업 유형 분류(추출, 소규모 수정, 다단계 구현, 시각 판독 등) | 권한·승인·삭제·배포 허용 여부의 최종 결정 |
| 난도·정밀도 점수화 | 옵션 호환성 검증(모델이 지원하는 추론/속도 값) |
| 위험 신호 탐지(파괴적 변경, 외부 영향, 보안 경계) | 입력 길이/모달리티 같은 결정적 조건 |
| 독립 검토 필요성, 병렬 가능성, 모호성 판정 | 복잡한 충돌 판정과 최종 승격 결정 |
| 자식 결과가 요구사항에 부합하는지 빠른 1차 검사 | 사실·보안·테스트 통과의 증명 |

Jev는 텍스트·추론·설명을 반환하지 않는다. 설명이 필요하면 별도 채팅 모델이나 부모가 근거를 작성해야 한다.[17]

## 제안 질문 세트 (v0, 검증 전)

한 요청에 독립 질문을 함께 보낼 수 있고 질문은 서로의 답을 보지 못한다.[20]

| 질문 | 형식 | 용도 |
|---|---|---|
| task_policy | Choice | L1/L2/M1/M2/F1/F2/V1/V2 중 추천. F3·E0는 분류기가 선택하지 않고 규칙/사용자 지시로만 진입 |
| reasoning_need | Score | 낮음/보통/높음 → 후보 변형의 추론 강도 선택 참고 |
| high_risk | Noul | 파괴적·외부 영향·보안·동시성 가능성. **위험만 올릴 수 있고 승인 면제 불가** |
| needs_independent_review | Noul | 독립 검토 추가 권고 |
| parallelizable | Noul | 독립 범위 분할 가능성 |
| ambiguous_requirements | Noul | 높으면 자식에게 보내기 전에 부모가 계약 보완 |
| visual_task | Noul | 이미지 판독/시각 추론 경로 후보 |

질문 문구와 기준은 TypeSafe 방식대로 입력 상태가 아니라 `criteria`에 정의한다. 이름은 이 설계에서의 임시 명칭이다.[22]

## 반드시 코드로 고정할 하드 규칙

분류 결과보다 먼저 적용하며 신경망 확률로 우회하지 않는다.

1. 현재 `delegate_task` option enum에 없는 경로는 선택 불가.
2. 모델의 추론 지원 집합 밖 값, 필수 추론 모델의 `none`, 미지원 속도 옵션 금지.
3. 이미지가 아닌 음성·영상 직접 전달 가정 금지.
4. 입력 길이 기반 제약(Haiku 100K 이상, 대형 컨텍스트 할증, 컨텍스트 초과) 적용.
5. 무료→유료 자동 전환 금지, 승인 필요한 외부 변경 금지.
6. 쓰기 소유권 충돌 시 직렬화.
7. 분류 실패·저확신 시 임의의 저가 경로로 낙하하지 않고 부모에게 이관.

이는 vLLM Semantic Router도 강조하는 순서와 같다. 자격 조건이 먼저 경로를 적합/부적합으로 만들고, 비용·지연 최적화는 그다음이다.[23]

## 비대칭 안전 정책

- `high_risk`가 높게 나오면 독립 검토·승인 요구를 **추가**할 수 있다.
- `high_risk`가 낮게 나와도 하드 규칙·사용자 승인 요구를 **제거할 수 없다**.
- 낮은 티어 추천은 하드 규칙과 모순이 없고 확신이 높으며 위험 질문이 낮을 때만 채택한다.
- 높은 티어 추천은 비용을 올리므로 부모가 필요성을 확인한다.
- 확신 지표는 작업 실행이 안전하다는 보증이 아니라 답변 분포의 집중도다. 임계값은 오류 비용으로 정한다.[20][24]

## 확신 처리 (초기 설계, 보정 필수)

TypeSafe 문서는 보수적 임계값에서 시작해 자체 데이터로 조정하고, 위험이 클수록 임계값을 높이라고 설명한다. Noul의 시작점으로 yes 0.7 / no 0.3을 제시한다.[24] 이 값은 출발점일 뿐 이 프로젝트의 검증값이 아니다.

| 영역 | 처리 |
|---|---|
| 추천 티어가 하드 규칙과 모순 | 즉시 폐기, 부모 이관 |
| 저위험 추출/변환 + 높은 확신 | 추천 채택 후보 |
| 일반 구현 | 추천을 참고하되 부모 확인 |
| 고위험 또는 모호성 높음 | 부모가 계약 보완·직접 결정 |
| 응답 실패/타임아웃/비정상 형식 | 부모 판단으로 대체. 분류기 오류를 작업 실패로 만들지 않음 |

## 비용·지연 (공개 가격 기반 추정, 미측정)

Jev 1.14는 OpenRouter 모델 페이지에서 입력 $0.042/M, 출력 $0, 컨텍스트 262K로 표시된다. 같은 페이지에서 P50 지연 약 0.11초가 보고되었다.[25] 입력 2,000토큰의 결정은 약 $0.000084이고 1,000건은 약 $0.084다. 이는 가격표 계산이며 실제 `usage.cost`와 지연은 우리 질문 세트에서 측정해야 한다. 상태를 길게 넣거나 질문을 늘리면 입력 토큰이 늘어 비용이 증가한다. 긴 입력·이미지에서의 지연과 정확도는 이 조사에서 확인하지 못했으므로 직접 측정한다.

고성능 부모 호출을 줄이는 이득은 분류가 정확하고 부모가 추천을 믿고 넘길 수 있는 비율이 충분할 때만 생긴다. 모든 건을 부모가 다시 판단하면 비용만 추가된다.

## 도입 단계

1. **그림자 모드:** Jev는 추천만 기록하고 실제 라우팅은 부모가 결정. 최소 표본을 모아 부모 판단·실제 성공·재작업·비용과 비교.
2. **보정:** 오분류 비용이 큰 방향부터 임계값 설정. 모델 버전은 고정(`typesafe/jev-1.14` 등)하고 `latest` 별칭은 임계값 재보정 전까지 사용하지 않는다. 문서 예시는 1.13과 1.14가 혼재하므로 호출 전에 모델 페이지에서 현재 ID를 재확인한다.[17][20][22]
3. **부분 위임:** 저위험 L1/L2 추천만 부모 확인 없이 채택. 위험·모호성 질문은 에스컬레이션 전용.
4. **재평가:** 승격률, 부모 이관율, 하향 라우팅 후 실패율, 총비용, 지연, 오분류 사례 검토. 성능이 부족하면 질문·기준을 수정하거나 사용 중단.

권장 통과 기준은 구현 전에 사용자와 확정한다. 최소한 고위험 정답 라벨에서 위험 누락이 0건이어야 하고, 저비용 경로 채택 후 승격률이 기존 부모 단독 판단보다 악화되지 않아야 한다. 구체 수치는 표본을 보고 정한다.

## Jev Router 평가

Jev Router는 요청마다 모델과 추론 강도를 선택하며, 비용 티어(`cost_tier`: low/medium/high)는 고정 모델이나 가격 상한이 아니라 라우팅 선호다. `models`/`allowed_models`는 라우팅 가능한 후보가 없으면 무시되는 선호 목록이고, `excluded_models`만 강한 제외다. 추론 강도(`reasoning.effort`)는 힌트일 뿐 최종 모델에 그대로 전달된다는 보장이 없다. 응답 메타데이터에 선택 모델과 후보별 예상 비용이 포함되지만 예상 비용은 실제 청구액이 아니다. 글로벌 데이터 리전과 허용된 워크스페이스에서만 사용할 수 있고 다른 라우터 모델과 결합할 수 없으며, 라우터가 불가하면 503을 반환한다.[16] 실제 청구 방식과 자동 대체 동작은 문서에서 확인하지 못했으므로 도입 전에 직접 검증한다.

따라서 정확한 모델·추론 옵션·속도 호환을 통제하는 이번 17개 변형의 기본 경로로 쓰기에는 부적합하다. 안전하게 고려할 수 있는 용도는 다음뿐이다.

- 별도 `Auto-Experiment` 경로로 실제 비용·품질을 비교
- 허용 모델/제외 목록으로 후보를 제한한 비교 실험
- 라우팅 메타데이터로 부모의 추천과 비교

현재 설치된 `model_map`은 `provider/model/base_url/api_key/api_mode/reasoning_effort/service_tier/fallback_providers`만 라우트로 전달한다. `plugins` 필드는 전달 경로가 확인되지 않았다. 따라서 `cost_tier`, 모델 포함/제외 목록을 서브에이전트 경로에서 쓸 수 있다고 가정하지 않는다. 가능한 것은 모델 ID만 지정한 기본 정책 실험이며 이것도 실호출 검증이 필요하다.

## 연결 방식과 막힌 점

| 방식 | 판단 |
|---|---|
| Docker 스크립트가 Decisions API 직접 호출 | 현재 Docker는 OpenRouter 키를 읽을 수 없어 불가. 키를 컨테이너로 전달하는 방식은 기존 격리 정책과 충돌 |
| 호스트 측 Hermes 플러그인 도구 `route_advice` | 가장 자연스러움. 키는 호스트에 두고 질문 세트·모델 고정·로그·실패 처리를 코드로 고정. 단 신규 플러그인 개발과 승인 필요 |
| Jev Router를 model_map 경로로 등록 | 설정 변경 승인과 실호출 검증이 필요. 위 제한 때문에 실험용으로만 |
| 전용 모델을 직접 자체 호스팅 | 이번 규모에는 과함 |

## 개인정보·운영 주의

- 분류 요청에 작업 설명과 파일 일부가 들어가면 외부 모델 호출이 된다. 비밀, 토큰, 개인정보, 창작 원문 전체를 보내지 않고 요약·메타데이터·길이·범위만 보낸다.
- 사용할 모델의 데이터 보존·학습 정책은 호출 전에 OpenRouter 모델 페이지와 개인정보 설정에서 확인한다. OpenRouter에는 요청별 ZDR 제한(`zdr`) 기능이 있으나, 이 기능이 Decisions API나 Jev Router에 동일하게 적용되는지는 이 조사에서 확인하지 못했다.
- 분류기를 도입해도 부모가 자식 결과의 근거를 검증하는 책임은 사라지지 않는다.
- 학습·보정용 로그에는 작업 원문 대신 필요 최소 필드(task_id, 질문, 확률, 부모 결정, 결과, 비용)를 저장한다.
